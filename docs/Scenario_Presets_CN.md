# SimAI 场景预设与仿真效果说明

本文按“场景预设—模拟方法—达到的效果”说明 `results/` 下已有的实验场景。文中的时间取自各结果目录现存的 `ncclFlowModel_EndToEnd.csv`，单位统一换算为毫秒。它们代表已有的一次仿真样本；涉及随机丢包、ECMP 哈希或并行调度时，应固定随机种子并多次运行后再形成统计结论。

## 通用仿真流程

所有场景采用同一条全栈仿真链路：先用 AICB 工作负载描述模型计算、并行组和集合通信，再由 SimCCL 将 AllReduce、AllGather、ReduceScatter、AllToAll 等集合通信拆成点到点流；随后，ASTRA-Sim 驱动 NS-3，在指定 Spectrum-X 拓扑、链路带宽、时延、丢包率、交换机缓存和拥塞控制参数下进行包级仿真。最终输出端到端完成时间、各并行维度暴露通信时间、流完成时间（FCT）、链路带宽、队列、PFC、RTT 和丢包等数据。

训练场景可使用：

```bash
./results/run_simai_scenario.sh <场景名> [负载文件名]
```

推理场景可使用：

```bash
./results/run_simai_inference_scenario.sh <场景名> [负载文件名]
```

## 1. Normal：正常网络基准

**场景预设。** 建立一个无故障、无随机丢包的标准训练网络，作为后续故障注入和网络优化实验的参照。当前新版基准使用 32 张 A100、每台服务器 2 张 GPU，训练并行参数为 TP=4、PP=2、EP=2、DP=4，序列长度为 2048；服务器上联为 100Gbps，机内 GPU 通信链路为 2400Gbps，叶脊链路为 800Gbps。

**模拟方法。** 在拓扑文件中将所有链路丢包率设为 0，保持 QCN、动态 PFC 阈值和 32MB 交换机缓存开启，不注入降速、增时延或链路中断。仿真器完整重放训练负载并记录通信完成时间及网络遥测，得到后续场景的基准值。

**达到的效果。** 当前结果中，训练迭代总时间为 **24.785ms**；其中 DP、TP 和 EP 的暴露通信时间分别为 14.194ms、6.441ms 和 0.726ms。该场景给出了健康网络下的正常性能边界，也提供了判断慢节点、丢包和拥塞影响的统一参照。

## 2. LatencyIncrease：单链路时延升高

**场景预设。** 模拟服务器 0 到叶交换机 48 的链路出现传播时延或设备处理时延异常，而链路带宽和丢包率保持不变，用于研究小消息、同步通信和集合通信对 RTT 增长的敏感程度。

**模拟方法。** 仅修改拓扑文件中 `0—48` 链路的时延，并保存了 0.0001ms、0.0005ms、0.001ms、0.005ms 和 0.05ms 五档结果；其余拓扑、工作负载、拥塞控制和缓存参数保持一致。SimAI/NS-3 在包级传输中自然累积额外 RTT，再由 ASTRA-Sim 将通信延迟反馈到训练关键路径。

**达到的效果。** 以 0.0005ms 档的 **24.785ms** 为同批基准，链路时延提高到 0.001ms、0.005ms 和 0.05ms 后，总时间分别为 **31.357ms、34.360ms 和 57.618ms**；最高时延档相对基准增加约 **132.5%**。结果说明，即使带宽没有变化，持续增加的链路时延仍会通过同步等待和集合通信轮次显著放大端到端耗时。

## 3. LinkSlowdown：核心链路降速

**场景预设。** 模拟网络关键路径上的核心链路性能退化，例如光模块、端口或链路协商异常造成骨干带宽下降。该场景将交换机 `48—50` 之间的带宽从正常值降低到 25Gbps，让大量跨域流量共同经过一条低速瓶颈。

**模拟方法。** 只在拓扑文件中降低核心链路带宽，保留原有工作负载和拥塞控制。NS-3 根据 25Gbps 的发送速率形成排队，ECN/PFC 和速率控制继续按真实队列状态工作；仿真结束后通过 FCT、队列、PFC、RTT 和端到端完成时间观察拥塞传播。

**达到的效果。** 当前遗留负载结果的总时间达到 **246.026ms**，并出现明显的长流 FCT 和同步等待放大。该预设成功制造了“整个通信域都被核心瓶颈拖慢”的效果，适合验证关键链路带宽监测和网络扩容策略。

## 4. SlowNode：单节点慢网卡

**场景预设。** 模拟单台训练服务器或其网卡成为慢节点。与核心链路降速不同，本场景仅把服务器 0 到叶交换机 48 的上联从 100Gbps 降低到 25Gbps，其余节点仍保持正常速率。

**模拟方法。** 在同一 32-GPU 训练负载和同一网络拓扑下，只修改 `0—48` 这一条主机上联。集合通信仍要求所有参与者完成，因此 SimAI 会把该节点较慢的发送和接收过程传递到 AllReduce、AllGather 等同步操作的完成时刻。

**达到的效果。** 当前结果总时间由 Normal 的 **24.785ms** 增长到 **191.679ms**，约增加 **673.3%**。这说明一个 25Gbps 慢节点就能成为全局同步的尾部节点，使其他 GPU 即使网络正常也必须等待，成功复现了分布式训练中典型的 straggler 效应。

## 5. SingleLinkError：单链路误码/丢包

**场景预设。** 模拟一条主机上联存在局部物理层或链路层质量问题，其他链路完全健康。故障注入点为 `0—48`，用于区分“单点坏链路”与“全网随机丢包”的影响。

**模拟方法。** 在拓扑文件的单条链路上分别设置 `1e-5`、`1e-4`、`3e-4` 和 `1e-3` 丢包率，其余 67 条链路丢包率为 0。NS-3 按给定概率丢弃数据包，RDMA 可靠传输、ACK/NACK 和重传机制负责恢复，仿真器记录由重传和同步等待造成的额外时间。

**达到的效果。** 四档结果的端到端时间分别为 **24.767ms、25.966ms、29.219ms 和 28.939ms**。总体上，误码率升高会增加重传和尾延迟；单次随机仿真不保证严格单调，因此 `3e-4` 与 `1e-3` 的顺序不能直接解释为更高丢包更快。该场景已经能够观察到单链路质量问题对全局集合通信的放大效应。

## 6. RandomLoss：全网上联随机丢包

**场景预设。** 模拟由线缆质量、交换芯片压力或网络环境扰动引起的分散型随机丢包。与 SingleLinkError 不同，故障不是集中在一条链路，而是覆盖 32 条服务器上联。

**模拟方法。** 对 32 条 100Gbps 主机上联统一设置 `1e-4`、`1e-3` 和 `1e-2` 三档丢包率，机内链路和核心链路保持无丢包。包级仿真会随机触发丢包、可靠传输恢复及相应的乱序/晚到事件，再统计端到端时间和 FCT 长尾。

**达到的效果。** 当前同批三档结果总时间为 **19.077ms、22.089ms 和 23.354ms**，随着全网上联丢包率升高，整体完成时间和慢流尾部均有恶化。该场景达到了“多数节点都偶发重传、平均退化有限但长尾更明显”的模拟效果，可用于评估网络健康度阈值和丢包告警策略。

## 7. PFCIngressCongestion：入口拥塞与 PFC 扩散

**场景预设。** 模拟某个接收入口持续承压，并在较小缓存下触发 PFC。服务器 0 的上联被限制为 50Gbps，同时交换机缓存由正常场景的 32MB 缩小为 4MB，用于制造更容易越过 PFC 阈值的入口拥塞。

**模拟方法。** 在拓扑中降低 `0—48` 链路带宽，在 `SimAI.conf` 中缩小 `BUFFER_SIZE`，保持动态 PFC 阈值和 QCN 开启。NS-3 根据入口队列水位生成 Pause/Resume，暂停会向上游传播；通过 PFC 状态、队列时延和 RTT 文件观察拥塞的产生与解除。

**达到的效果。** 当前结果总时间从 Normal 的 **24.785ms** 增长到 **77.017ms**，约增加 **210.7%**。该场景成功产生了由小缓存、入口速率不匹配和无损流控共同引起的停顿，能够用于分析 PFC 风暴、头阻塞及缓存阈值配置。

## 8. HotspotCongestion：MoE 热点流量

**场景预设。** 模拟 MoE 专家负载不均或 token 路由倾斜造成的热点通信。场景不破坏物理网络，而是把四次 `ALLTOALL_EP` 的单次消息量从 512KiB 增大到 64MiB，即放大 128 倍，让专家并行流量集中冲击网络。

**模拟方法。** 保持拓扑和网络控制参数不变，只修改 AICB 工作负载中的 EP All-to-All 消息大小。SimCCL 将放大后的集合通信拆成更多大流，NS-3 负责模拟这些流在相同链路和缓存上的竞争，从而观察热点造成的队列、FCT 和 EP 暴露通信时间变化。

**达到的效果。** 当前结果总时间为 **110.908ms**；已有对比分析还显示 EP 暴露通信和相关 MoE 层受到最明显冲击。该预设成功将“业务侧流量倾斜”转换成网络热点，适合验证专家负载均衡、All-to-All 优化和热点感知路由。

## 9. Large：大消息通信压力

**场景预设。** 模拟模型规模、隐藏层宽度、序列长度或 batch 增长后，绝大多数通信张量同步变大的情况。该场景把 PP 消息及 attention、MoE、cross-entropy 等主要通信消息整体放大约 10 倍，而优化器中的极小控制消息保持不变。

**模拟方法。** 仅放大工作负载文件中的通信字节数，物理拓扑仍保持健康。SimCCL 根据新消息量产生更大的通信流，NS-3 计算链路占用和排队，最终由端到端结果展示大消息对各并行维度的影响。

**达到的效果。** 当前结果总时间为 **28.978ms**。该场景使通信从短小突发转向更长时间占用链路，便于观察链路吞吐上限、消息分片和拥塞控制在大流条件下的行为。由于该目录使用的是 seq512 遗留负载，不能直接与新版 seq2048 Normal 数值计算收益或退化比例。

## 10. CPE：双核心路径扩容预设

**场景预设。** CPE 是早期的 Critical Path Expansion 预设：在叶交换机 48、49 之间设置两个核心交换机 50、51，每条叶脊链路为 1600Gbps，用并行等价路径提高关键路径聚合容量。

**模拟方法。** 在拓扑中增加一台核心交换机及对应链路，保持服务器上联、工作负载和拥塞控制不变。NS-3 使用 ECMP 五元组哈希将不同流分配到两条路径，同一条流仍固定走一条路径；通过各核心交换机的带宽和 trace 记录检查是否发生分流。

**达到的效果。** 当前遗留结果总时间为 **19.244ms**。场景能够展示多路径带来的分流和关键路径卸载效果，但由于它属于早期拓扑版本，主要用途是做机制验证；需要严谨量化时应使用下一节的 CriticalPathExpansion 参数扫描。

## 11. CriticalPathExpansion：关键路径扩容参数扫描

**场景预设。** 在 Normal 的关键路径上系统比较“1 台还是 2 台核心交换机”“叶脊 400Gbps 还是 800Gbps”以及“主机上联 100Gbps 还是 400Gbps”，用于分辨路径数量、核心带宽和接入带宽分别能带来多少收益。

**模拟方法。** 保存六组完全可复现的拓扑和配置快照：`1psw-400gbps`、`1psw-800gbps`、`1psw-800gbps-400gbps`、`2psw-400gbps`、`2psw-800gbps`、`2psw-800gbps-400gbps`。其中 `-400gbps` 后缀组合表示主机上联也升到 400Gbps；1psw/2psw 用于控制 ECMP 路径数量。各组使用同一个 seq2048 训练负载。

**达到的效果。** 六组总时间依次为 **31.532ms、24.785ms、22.818ms、29.366ms、24.562ms 和 16.788ms**。只增加第二条 800Gbps 核心路径时，总时间从 24.785ms 小幅降至 24.562ms，说明此时 100Gbps 主机上联仍限制收益；当主机上联同时升到 400Gbps 后，双路径方案降至 16.788ms，相对 1psw-800gbps 基准缩短约 **32.3%**。该扫描清楚证明了扩容需要同时消除接入侧和核心侧瓶颈。

## 12. Megatron：训练并行策略搜索

**场景预设。** 在相同 32-GPU MoE 训练任务上组合不同的 TP、PP、EP 参数，并额外提供带 AIOB 计算时间的端到端工作负载，用于寻找计算、数据并行、张量并行、流水并行和专家并行之间的平衡点。

**模拟方法。** AICB/Megatron 为每组并行参数生成不同的计算与通信序列，SimCCL 和 NS-3 在相同网络上逐组重放。纯通信版本主要比较网络代价；`Megatronwithaiob` 版本把采集到的计算时间也写入工作负载，从而评估计算与通信共同构成的完整迭代时间。

**达到的效果。** 现有纯通信结果中，TP=4、PP=2、EP=4 的组合最短，为 **10.159ms**；其他主要组合分布在 10.756–20.021ms。带 AIOB 的结果显示计算通常占总时间的 90% 以上，总时间分布在 157.056–498.660ms。该场景既找到了当前样本下较优的通信并行组合，也揭示了只优化网络和纳入真实计算时间后结论可能不同。

## 13. Prefill：32-GPU 推理预填充

**场景预设。** 模拟 Qwen3-MoE-235B 在 32 张 GPU 上处理长度为 512 的输入提示，重点研究 Prefill 阶段的大矩阵计算和大张量通信，以及 TP、PP、EP 切分方式对首阶段时延的影响。

**模拟方法。** 使用推理工作负载文件描述一次 Prefill 的计算和集合通信，针对 TP=4/8、PP=1/2、EP=2/8 等组合运行 SimAI，并在相同 100Gbps 服务器网络上记录端到端完成时间和各并行维度通信占比。

**达到的效果。** 已完成的三组结果中，TP=8、EP=2 的两种 PP 设置均为 **72.555ms**，TP=4、PP=1、EP=8 为 **113.089ms**。该预设表明在当前模型和拓扑下，提高 TP 并控制 EP 规模能显著缩短 Prefill 时间，同时也为定位 TP/EP 通信瓶颈提供了数据。

## 14. Prefill2：64-GPU 大规模预填充扩展

**场景预设。** 将 Prefill 搜索空间扩展到 64 张 GPU，覆盖 TP=2–32、EP=2–32 的更宽参数范围，用于观察规模扩大后并行切分是否仍能带来线性收益。

**模拟方法。** 为每个 64-GPU 并行组合生成独立工作负载并逐个仿真，保持模型、batch 和序列长度一致，通过端到端时间比较过低或过高 TP/EP 带来的通信代价。

**达到的效果。** 当前已有结果中，TP=4、EP=8 最短，为 **119.519ms**；其余组合为 134.316–290.103ms，TP=32、EP=2 最慢。结果说明增加 GPU 数量本身不会自动缩短 Prefill，过大的 TP 会增加高频张量通信，应在模型切分能力和网络代价之间寻找中间点。

## 15. Decode：逐 token 解码

**场景预设。** 模拟 Qwen3-MoE-235B 在 32 张 GPU 上、batch=1 的 Decode 阶段。Decode 的单步计算和通信粒度较小、同步频率高，因此该场景主要评估不同并行方式对单 token 生成时延的影响。

**模拟方法。** 使用 Decode 专用工作负载，扫描 TP=2/4/8、PP=1/2/4、EP=2/4/8 等组合。SimAI 重放每一步的点对点和集合通信，输出单次工作负载总时间，从而比较不同模型切分方式带来的细粒度同步开销。

**达到的效果。** 当前结果中，TP=2、PP=2、EP=2 最短，为 **1.882ms**；TP=2 的其他组合约为 1.999–2.023ms，TP=4 增至 4.071ms，TP=8 则约为 7.8ms。该场景清楚显示 Decode 对过大的 TP 更敏感：小消息的高频同步无法充分利用更多分片，反而会增加每 token 延迟。

## 场景之间的使用关系

- Normal 用于建立健康网络基线。
- LatencyIncrease、LinkSlowdown、SlowNode、SingleLinkError、RandomLoss 和 PFCIngressCongestion 用于注入不同类型的网络异常。
- HotspotCongestion 和 Large 从业务负载侧制造压力，用于区分“网络坏了”和“流量本身变重了”。
- CPE 与 CriticalPathExpansion 用于验证 ECMP 和关键路径扩容，其中后者是参数更完整、对比更严格的新版本。
- Megatron 用于训练并行策略搜索；Prefill、Prefill2 和 Decode 用于推理阶段与并行策略搜索。

做正式对比时，应确保两个场景使用同一个工作负载、同一版拓扑、相同随机种子和调度策略；否则只能描述各自的绝对结果，不能直接把差值归因于某一个场景参数。
